# ExecPlan standard

Каждый ExecPlan является самодостаточной инструкцией для Codex и живым журналом исполнения.

## Required sections

### 1. Outcome

Пользовательский или системный результат одним абзацем. Не перечень файлов.

### 2. Why this plan exists

Как результат связан со `SPEC.md`, какая предыдущая capability требуется и что станет возможным после завершения.

### 3. In scope

Исчерпывающий список поведения этой итерации.

### 4. Out of scope

Смежные функции, которые запрещено добавлять в этой итерации.

### 5. Preconditions

Необходимые решения, инструменты, сервисы и предыдущие milestones.

### 6. Contracts and invariants

API, database, domain, security, tenancy, observability и compatibility requirements.

### 7. Milestones

Каждый milestone должен:

- оставлять репозиторий в запускаемом состоянии;
- иметь наблюдаемый результат;
- иметь точные validation commands;
- перечислять ожидаемые файлы, но не навязывать бессмысленную структуру;
- включать failure-path tests.

### 8. Acceptance criteria

Только проверяемые утверждения. Избегать формулировок «качественно», «production-ready» без метрики или теста.

### 9. Validation commands

Команды должны запускаться из корня репозитория. Указать ожидаемый exit code и, где полезно, ключевой фрагмент результата.

### 10. Demo

Короткий сценарий, который человек может выполнить после завершения.

### 11. Rollback and recovery

Как вернуть предыдущую рабочую версию; как очистить только артефакты данного плана; какие данные нельзя удалять автоматически.

### 12. Progress

Checklist с датой/временем и фактическим результатом. Обновляется во время работы.

### 13. Discoveries

Неожиданные свойства кода, инструментов или интеграций, которые повлияли на реализацию.

### 14. Decision log

Локальные решения, которые не заслуживают отдельного ADR. Значимые необратимые решения оформляются ADR.

### 15. Final evidence

Команды, exit codes, ссылки на тестовые отчёты, screenshots/trace IDs при наличии.

## Stopping rules

Codex обязан остановить milestone и запросить решение, если:

- требуется изменить утверждённый ADR;
- обнаружен риск удаления пользовательских данных;
- нужен реальный production secret;
- нужная лицензия несовместима;
- acceptance criterion невозможно проверить в текущей среде;
- требуется материальное расширение scope.

Обычные ошибки сборки, тестов и типов не являются причиной останавливаться: их нужно исправлять в рамках milestone.
