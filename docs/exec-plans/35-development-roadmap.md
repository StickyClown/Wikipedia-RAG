# ExecPlan 35: Путь развития WikipediaRag

## Цель

Развить WikipediaRag из локального рабочего RAG-проекта в более универсальную систему для поиска, чата по знаниям и глубокого исследования по документам.

Проект не переписывается на другую платформу. Развитие идёт поверх текущей основы: API, база данных, файловое хранилище, поисковый индекс, фоновая обработка документов, роли пользователей и проверка ответов.

## Текущая точка

Уже есть:

- загрузка документов;
- импорт Wikipedia;
- фоновая обработка файлов;
- поиск по базе знаний;
- чат с источниками;
- роли пользователей и баз знаний;
- поиск по нескольким базам знаний;
- проверка цитат;
- журнал шагов поиска;
- экран отладки поиска;
- обычный поиск через hybrid retrieval pipeline;
- навигация по загруженным документам: оглавление, поиск внутри документа и контекст соседних фрагментов;
- основы подключения внешних источников: source records, sync runs, changed/deleted source document handling и Stage 4 connector contract.
- durable Deep Research V1: single-KB research runs, typed evidence memory,
  coverage records, operational reflections, pause/resume/cancel и compact UI.

Следующий Pareto-инкремент после Deep Research V1 реализован: bounded
single-agent planner/tool loop вызывает только `extended_search`, сохраняет
безопасный tool ledger, создаёт derived questions с lineage и сохраняет
проверенные claims. Mock runtime smoke и offline quality/context matrix
выполнены. Новый следующий шаг теперь более узкий: стабилизировать изолированный
OpenRouter/Qwen hard gate, затем сравнить runtime policy 45% и 35% без
ухудшения безопасности. Полный Qwen hard pack пока не прошёл общий
900-секундный deadline, поэтому он не является основанием менять default.
Минимальный document-level ACL/security trimming уже реализован поверх trusted `metadata.document_access`:
обычные документы остаются KB-visible, restricted-документы видят только
админы/KB managers/owners или явно разрешённые users/groups.

## Этап 1. Закрепить текущую версию

Что сделать:

- выполнить текущие проверки в Docker;
- записать команды, результаты и найденные ограничения;
- обновить статус проекта;
- не добавлять новые функции, пока текущая версия не подтверждена проверками.

Результат:

- есть понятная стабильная точка, от которой можно развивать проект дальше.

## Этап 2. Добавить обычный поиск

Статус: реализовано. Обычный viewer-scoped `POST /api/v1/search` использует
hybrid retrieval pipeline, фильтры, pagination, facets, grouping и открытие
результата в document viewer.

Что сделать:

- добавить отдельный экран поиска;
- показывать найденные документы списком;
- показывать краткие выдержки, раздел, источник и дату;
- добавить фильтры по базе знаний, типу документа, языку, дате и источнику;
- дать возможность открыть найденное место в документе.

Результат:

- проект становится не только чатом, но и полноценным поиском по знаниям.

## Этап 3. Улучшить навигацию по документам

Статус: реализовано. Система хранит `document_sections`, поддерживает открытие
чанка/раздела, поиск внутри документа и соседний контекст для загруженных
документов.

Что сделать:

- хранить структуру документа: заголовки, разделы, страницы и соседние части текста;
- добавить оглавление документа;
- добавить поиск внутри одного документа;
- добавить открытие конкретного раздела;
- добавить просмотр соседних фрагментов вокруг найденного места.

Результат:

- система сможет точнее находить и показывать нужные места, а не только отдельные куски текста.

## Этап 4. Подготовить подключение внешних источников

Статус: реализовано как foundations. Есть `knowledge_sources`,
`source_sync_runs`, `source_document_states`, regular refresh metadata,
changed/deleted source document handling и connector contract для Stage 4
источников.

Что сделать:

- ввести единый способ подключения источников;
- хранить источник документа, время обновления и состояние документа;
- поддержать регулярное обновление;
- учитывать удалённые документы;
- добавлять изменённые документы без полной перезагрузки всей базы.

Результат:

- проект можно будет расширять до работы с папками, хранилищами, сайтами и корпоративными источниками.

## Этап 5. Усилить права доступа

Статус: реализовано минимально. Поиск, чат, отладка, Extended Search neighbor
expansion, Multi-KB retrieval и document viewer применяют общий
`DocumentAccessScope`; direct uploads не могут выставить restricted ACL,
trusted source sync metadata может.

Что сделать:

- добавить права на отдельные документы;
- связывать документы с пользователями и группами;
- скрывать запрещённые документы во всех поисковых и чат-путях;
- проверять смену прав без полной перестройки базы;
- добавить проверки против показа чужих документов.

Результат:

- система сможет безопасно работать с несколькими группами пользователей и разными уровнями доступа.

## Этап 6. Сделать поиск умнее

Что сделать:

- определять тип вопроса перед поиском;
- отдельно обрабатывать точные факты, даты, имена, сравнения, общие вопросы и вопросы без ответа;
- для сложных вопросов запускать несколько поисковых шагов;
- для важных утверждений включать строгую проверку;
- сохранять выбранный путь поиска для отладки.

Результат:

- система будет меньше ошибаться на точных вопросах, похожих сущностях и сложных сравнениях.

## Этап 7. Сохранять путь к ответу

Статус: реализовано V1. `query_runs`/`retrieval_events` сохраняют trace для
чата, debug и Deep Research episode retrieval; `research_evidence_records`,
`research_claim_records` и `research_coverage_records` сохраняют типизированную
память и покрытие на уровне durable research run.

Что сделать:

- хранить не только итоговый ответ, но и то, как он был получен;
- сохранять найденные подтверждения;
- связывать утверждения ответа с источниками;
- сохранять недостающие сведения;
- сохранять причину остановки: ответ найден, данных мало, есть противоречие или произошла ошибка.

Результат:

- ответы можно будет проверять, сравнивать и разбирать без повторного запуска вопроса.

## Этап 8. Добавить глубокое исследование

Статус: реализовано V1 как single-KB durable lifecycle с bounded planner/tool
loop. Runs создаются через
`/api/v1/research-runs`, исполняются worker job `deep_research`, чекпойнтятся
после каждого episode, поддерживают pause/resume/cancel и показываются в
компактной UI-панели. В каждом episode planner валидируется сервером и может
вызвать только `extended_search`; найденные aliases/exceptions/owners/blockers
могут стать deduplicated `derived` questions. Claims проходят verification до
уверенного вывода. Multi-KB, web browsing, meta-loop и тяжелый multi-agent
runtime не входят в V1.

Что сделать:

- принимать большую тему или сложный вопрос;
- разбивать его на части;
- искать подтверждения по каждой части;
- отмечать, что покрыто, что частично покрыто, чего не хватает и где есть противоречия;
- собирать итоговый отчёт только из подтверждённых материалов;
- дать возможность остановить и продолжить длинную задачу.

Результат:

- проект сможет готовить исследовательские отчёты, а не только короткие ответы.

## Этап 9. Улучшить проверки качества

Статус: реализованы deterministic fixtures, offline evaluator, runtime smoke
CLI и offline multi-policy context matrix. Полный mock runtime smoke прошёл
10/10 fixtures; offline matrix прошла 27 policy aggregates / 270 fixture-policy
rows и рекомендовала `target_35_abstracts_only_none` как самый экономный
synthetic packer policy. Это не меняет runtime default автоматически: нужен
runtime policy override и локальная/Qwen-проверка перед сменой текущего 45%
профиля. Дополнительно добавлен hard-набор
`tests/fixtures/deep_research/research_tasks_hard.json`: он не является
обычным smoke-набором, а фиксирует regression target для уже реализованных
tools, alias resolution, chain-of-sources и query reformulation. Изолированный
mock preflight подтвердил alias chain end-to-end; полный OpenRouter/Qwen pack
пока не прошёл deadline, поэтому policy exception, contradiction и finance
chains остаются целями валидации, а не подтверждёнными результатами.

Что сделать:

- добавить небольшой набор сложных вопросов прямо в проект;
- проверять точные даты, редкие имена, похожие названия, ложные предпосылки, вопросы без ответа и сравнения;
- отдельно измерять качество поиска, качество ответа, точность ссылок, скорость и безопасность доступа;
- для ошибок сохранять причину: не найден документ, найден не тот фрагмент, ошибка проверки, слабое подтверждение или ошибка выполнения.

Результат:

- станет понятно, какие изменения реально улучшают систему, а какие только усложняют её.

## Этап 10. Отложить сложные графовые подходы

Что сделать:

- не делать графовый поиск основным путём сейчас;
- рассматривать его только как отдельное дополнение для сложных связных вопросов;
- перед внедрением подготовить отдельный план, проверки и критерий пользы.

Результат:

- проект не усложняется преждевременно и развивается через более полезные базовые улучшения.

10. Отдельно исследовать графовый поиск.

## Критерии готовности

Развитие считается успешным, если:

- обычный поиск работает отдельно от чата;
- пользователь может найти документ и открыть нужное место;
- доступы применяются на уровне документов;
- сложные вопросы обрабатываются в несколько шагов;
- ответ связан с подтверждениями;
- длинное исследование можно остановить и продолжить;
- проверки качества показывают улучшение без ухудшения безопасности.
